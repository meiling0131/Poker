# 机器人求解器训练方案（H100）

目标：在这个 7 人桌、100BB 深度的无限注德州扑克游戏里，把机器人练到"很难被针对、稳定赢普通玩家"的水平。训练放在一台 H100（GPU）加多核 CPU 的机器上离线做；牌桌上只查表，不需要显卡。

本文是整体方案。现成能跑的步骤见 [H100_PROMPT.md](H100_PROMPT.md)（第一晚）；各工具的用法见 [README.md](README.md) 和 [../flops/README.md](../flops/README.md)。

---

## 0. 参考：Sequoia × Citadel Securities × OpenAI 的 No Limit 机器人比赛

2026 年 11 月，Sequoia 联合 Citadel Securities 和 OpenAI 办了一个扑克机器人比赛 “No Limit: A Bot Building Tournament”：

- **赛制**：1–2 人一队，60 分钟从零写出机器人，然后机器人之间对打几千局，分六轮计分。
- **代码**：用 Python 实现官方给的 Agent 接口，官方提供本地模拟器。
- **限制**：比赛时离线运行，**每步 1 毫秒内**做出决定，超时或报错自动弃牌/过牌；不能联网、不能调用任何 API。写代码时可以用 AI 编程助手。
- **打的是哪种扑克**：当天开始写代码时才公布。
- **其他**：面向美国大学在校生和 2025/2026 届毕业生；波士顿、匹兹堡、湾区三个分赛区，旧金山决赛，冠军 10 万美元。

对我们的启发：

1. **牌桌上必须快**：比赛每步 1 毫秒。我们的机器人在浏览器和 Cloudflare 服务器里跑，预算宽一些（每步约 10 毫秒），但道理一样：重的计算全部离线做完，牌桌上只查表和做少量计算。这正是现在的架构，下面的方案保持这一点。
2. **规则可能临时变**：比赛当天才公布玩法，所以通用、可重新配置的求解器流程比只针对一种玩法的代码更值钱。我们的求解器已把下注尺寸、起始范围、底池路线都放在配置里，后面加三人底池也按这个思路。
3. **对手是机器人，打几千局**：偶然性很大，一定要用降低偶然性的评估方法（下面的阶段 A），不能凭几百手的结果下结论。

## 1. 目标、约束和现状

**机器人的决策都发生在哪里**：在 600 手模拟里，机器人翻牌后的决策——

| | 单挑 | 三人 | 四人以上 |
|---|---|---|---|
| 全部 | 79% | 19% | 2% |
| 翻牌 | 68% | 29% | 3% |
| 转牌 | 88% | 11% | 1% |
| 河牌 | 96% | 4% | — |

**运行时约束**：
- 每步计算不超过 10 毫秒（浏览器练习模式和 Cloudflare Durable Object）。
- 所有表合计压缩后不超过约 3MB（随页面加载，也打进服务器代码）。
- 浏览器和服务器里都没有 GPU。

**现在已有的**：

| 部分 | 做法 | 状态 |
|---|---|---|
| 翻牌前 | 标准 7 人桌起手牌表（`js/preflop.js`），边缘牌混合 | 已上线 |
| 单挑翻牌后 | GPU 上的 Discounted CFR，每街 10 个手牌分组，五条翻牌前路线（`tools/solver`） | CPU 粗糙版已上线，H100 版待训练 |
| 精确翻牌 | 开源 postflop-solver 精确求解约 320 个翻牌，按牌面类别 × 决策点 × 手牌类别整理（`tools/flops`） | 流程已就绪，待在 H100 机器上编译运行 |
| 多人底池 | 机器人自己的规则 | 已上线 |
| 对手适应 | 根据统计（偷盲、弃牌率、持续下注、摊牌诈唬）调整表的策略；跟注站改用自己的规则 | 已上线 |
| 评估 | 脚本玩家（诈唬型、偷盲型、紧凶型、跟注站）对打（`tools/exploit.js`） | 已有，偶然性大 |

## 2. 路线图

| 阶段 | 内容 | 主要算力 | 时间 | 必要性 |

### 阶段 A：先把"怎么判断变强了"做扎实

扑克的偶然性极大：现在每局 1500 手、三个种子，单个种子的结果能差一百多 bb/100。没有可靠的评估，后面所有训练都没法判断好坏。

1. **对位复式对打**（`tools/duel.js`，新写）
   - 同一副牌发两遍，新旧两版机器人互换座位各打一次，结果相减。运气（谁拿到好牌）基本抵消，偶然性降低一个数量级。
   - 7 人桌：每次只换一个座位上的版本，轮转座位。
   - 输出：每 100 手赢多少大盲（bb/100）、95% 置信区间、需要多少手才能分出高下。
   - 规模：headless 模拟每核每分钟约 300 手，64 核 10 分钟能打 20 万手。
2. **局部最优反击（Local Best Response, LBR）**（`tools/lbr.js`，新写）
   - 一个"开了天眼"的对手：它能看到机器人的策略表，根据机器人到目前为止的行动推算其手牌范围，每一步选期望最高的动作。
   - 机器人越难被它赢钱，说明越接近均衡。它是衡量"可被针对程度"的标准方法（Lisý & Bowling 2017）。
3. **保留脚本玩家对打**（`tools/exploit.js`）：诈唬型、偷盲型、紧凶型、跟注站，确认没有明显的套路能赢。
4. **上线门槛**（之后每一阶段都按这个判断）：
   - 复式对打：新版对旧版的胜率 95% 置信区间下限大于 0，或者没有显著变差，同时 LBR 明显下降；
   - LBR 赢率比旧版低；
   - 四种脚本玩家没有任何一种比旧版多赢 20 bb/100 以上；
   - 每步计算 ≤ 10 毫秒，表大小在预算内。

### 阶段 B：单挑蓝图 v2（H100，一晚）

在现有 GPU 求解器（`tools/solver/solve.py`）上改进三处：

1. **更细的手牌分组**：从每街 10 组改成每街约 48 组。
   - 翻牌、转牌：12 种牌型类别（暗三、两对、超对、顶对、组合听牌……，和 `js/flops.js` 同一套）× 4 档类别内强度（对随机手牌的期望胜率四分位）。
   - 河牌：40 档当前胜率（河牌胜率可以精确算，很便宜）。
   - 这样同组里的牌打法更接近；JS 端算这些很快，用的都是现成函数。
   - 研究上更好的分组是按胜率分布聚类（EMD 距离 k-means，Ganzfried & Sandholm 2014），但它要在牌桌上算胜率分布，超出 10 毫秒预算，所以暂不采用。
2. **更多下注尺寸**：翻牌 1/3、3/4、1.25 倍；转牌 1/2、1、1.5 倍；河牌 1/3、3/4、1.25 倍、全下；加注 2.5 倍和全下；每街最多 3 次加注。
3. **GPU 提速**：
   - 树是固定的，用 CUDA Graphs 把一整轮迭代录下来重放，省掉 Python 每个节点的调度开销，预计 5–10 倍；
   - 摊牌计算改写成 Triton 内核；
   - batch 加到 8192。

预算：最大的单加注底池每轮约 1 秒，每条路线 1 万轮约 3 小时；五条路线放在一张 H100 上并行。表的大小约 1.5–2MB，没有到达过的格子不存。

验收：按阶段 A 的门槛和现在线上的 CPU 版对比；`show.py` 检查已知问题，比如转牌面对下注中等牌弃太多。

### 阶段 C：精确翻牌，扩大规模并给蓝图打分（CPU，一晚）

1. **扩大规模**：现在挑约 320 个代表性翻牌。CPU 核数够（≥128 核）就解全部 1755 种不同翻牌，牌桌上直接按花色同构找到同一个翻牌，不用再按类别平均。表的大小会到几 MB，需要压缩（每手牌 4 bit），或只给服务器用。
2. **给蓝图打分**：postflop-solver 支持锁定一方的策略。
   - 把一方的翻牌策略锁成 GPU 蓝图的策略，让求解器为另一方算出最优反击，就能得到"我们的蓝图在真实翻牌上会被剥削多少"，单位是底池的百分比。
   - 这是比脚本对打更准的指标，每次训练后都能跑一遍，找出哪些牌面、哪些决策点最差。

### 阶段 D：三人底池蓝图（CPU 多核，开发 2–3 天 + 一晚）

覆盖翻牌时 29% 的决策。

- **路线**：按出现频率选 2–3 条，比如：
  - 后位开池、一人跟、大盲跟（三人单加注底池）；
  - 小盲补、大盲过、一人跛入（三人跛入底池）。
- **算法**：Pluribus 用的 Linear MCCFR（外部抽样 + 负遗憾剪枝）。
  - 三个人的手牌组合约 23 亿种，不能像单挑那样全部一起算，只能每轮抽具体的手牌。
  - 三人局没有收敛到均衡的理论保证，但 Pluribus（2019，6 人桌赢顶级职业选手）证明了实践中有效。
- **实现**：Rust 多线程（抽样遍历是分支很多的串行逻辑，不适合 GPU），手牌分组和下注尺寸与阶段 B 一致；信息集键加上"三人中第几个行动""还剩几个人"。
- **算力参考**：Pluribus 的 6 人桌全游戏蓝图在 64 核机器上算了 8 天。我们只解翻牌后的几条三人路线，分组也粗，估计 64 核一晚可以得到可用的结果。
- **运行时**：`js/gto.js` 加三人局的键；四人以上继续用机器人自己的规则。

### 阶段 E：运行时改进

1. **伪调和映射（必须做）**：你下的注不在表里的尺寸上时，现在是归到最近一档，这容易被针对，比如专门下两档中间的尺寸。改成按伪调和公式（Ganzfried & Sandholm 2013）在相邻两档之间随机归档：
   - x 落在表里相邻两档 A < x < B 之间（都按底池比例算），以概率 ((B−x)(1+A)) / ((B−A)(1+x)) 归到 A，否则归到 B。
   - 改动小，效果明确。
2. **河牌实时重解（可选）**：河牌是单挑、钱最多的地方。
   - 做法：按蓝图推算双方到河牌时的手牌范围，用实际的下注尺寸在 JS 里把河牌这一小局重新解几百轮（单挑河牌全组合，向量形式）。
   - 这是 Libratus 战胜职业选手的关键技术之一（安全子博弈求解）。
   - 代价：每步约 50–150 毫秒，需要评估服务器 CPU 预算是否够。

### 阶段 F：小型 BERT 策略网络（数据用 CPU，训练用 H100）

**为什么用 Transformer**
- 表有三个先天问题：
  - 手牌分组粗；
  - 信息集不记完整历史，不同行动线共用一个策略；
  - 表里没有的下注尺寸要映射，多人局还要另做表。
- 小 BERT 把一手牌的整个过程当成一串 token：手牌、公共牌、每个行动（谁、做了什么、下多少）。
  - 自注意力看得到完整历史，不用人工设计历史特征；
  - 人数、下注尺寸、筹码深度都可以变，多人局天然支持；
  - 一个约 100KB 的网络就能代替几 MB 的表。
- 先学**模仿精确求解器**（监督学习，最稳）；之后再考虑自博弈微调（可选）。

**输入 token**（最多约 24 个，通常 15–20 个）
- `[CLS]`
- **局面**：街、我在剩下的人里第几个行动、还剩几个人、SPR 档、要跟注的价格档。
- **牌**：2 张手牌 + 3–5 张公共牌，每张 = 点数嵌入 + 花色嵌入 + 位置嵌入（手牌/翻牌/转牌/河牌）。
  - 花色先按牌面规范化（花色同构）；
  - 训练时再随机换花色做数据增强。
- **行动**：每个行动一个 token = 行动者（相对我的位置）+ 类型（过牌/跟注/下注/加注/全下/弃牌）+ 尺寸（占底池比例，16 档对数分档）+ 街。

**模型和速度**（实测，纯 JavaScript，最后一层只算 `[CLS]`）

| 规模 | 参数 | int8 大小 | 每步用时 |
|---|---|---|---|
| 宽 64、2 层 | 6.6 万 | 64KB | 2.8 毫秒 |
| **宽 64、3 层、4 头、前馈 128（选这个）** | **9.8 万** | **96KB** | **4.8 毫秒** |
| 宽 96、3 层 | 22 万 | 216KB | 11 毫秒（超预算） |
| 宽 128、4 层 | 52 万 | 512KB | 28 毫秒（超预算） |

- **输出**：`[CLS]` → 8 个动作的概率（弃牌、过牌/跟注、下注或加注到 1/3、1/2、3/4、1 倍、1.5 倍底池、全下），不合法的动作屏蔽掉。
- 另一个输出头预测这手牌的期望收益，只用来辅助训练。

**训练数据**（先做单挑）
- postflop-solver 解一个翻牌时，转牌和河牌其实也全解了，只是我们现在只导出翻牌。
- 扩展 `tools/flops/solver`：每个翻牌随机抽 8 张转牌 × 4 张河牌，把沿途每个决策点、每手牌的精确策略和到达概率都导出来。
- 规模：600 个翻牌 × 5 条路线 × 每个约 800 个决策点 × 每点抽 64 手牌 ≈ 1.5 亿条样本。用 CPU 多核跑一两晚。
- 留出 10% 的翻牌完全不参与训练，专门检验对没见过的牌面的泛化。

**训练**（H100）
- AdamW，bf16，batch 8192，约 2–6 小时。
- 损失 = 按到达概率加权的 KL 散度（学求解器的混合策略，不是只学最常选的动作）+ 0.1 × 期望收益回归。

**导出和运行时**
- 权重量化成 int8，写成 `js/net-weights.js`。
- `js/net.js` 手写前向计算：嵌入、LayerNorm、注意力、GELU、softmax。
- 一致性测试：1000 个随机局面上 JS 和 PyTorch 的输出对比。
- 查询顺序：网络 → 精确翻牌表 → GPU 表 → 机器人自己的规则。之后照常经过对手适应和性格层。
- 安全护栏保留在网络外面：价格合适时不弃牌、对跟注站用自己的规则。

**评估**
- **模仿程度**：在留出的翻牌上，和求解器的 KL 散度、首选动作一致率。
- **可剥削度**（最关键）：在留出的翻牌上，把一方所有决策点的策略锁成网络的，让 postflop-solver 算最优反击，得到被剥削多少（底池百分比），再和 GPU 表、精确解（约 0.5%）对比。
- 阶段 A 的复式对打、LBR、脚本玩家。

**第二步（可选）：多人局**
- 用阶段 D 三人 MCCFR 的结果当训练数据；
- 或者用自博弈强化学习微调。参考 AlphaHoldem（AAAI 2022）：端到端自博弈，单机 8 卡训练 3 天，每步 2.9 毫秒。
- 潜力大但不稳定，必须过阶段 A 的门槛。

**局限**
- 模仿学习学不过老师：在求解器覆盖的局面（单挑、它用的下注尺寸）上，网络最多和求解器一样好。
- 收益来自四方面：完整历史；对没见过的翻牌、尺寸、深度的泛化；体积小；能扩展到多人局。
- 网络可能在罕见局面给出离谱的动作，所以安全护栏放在网络外面，并用可剥削度检查。

### 不做的（以及为什么）

- **DeepStack / ReBeL / Student of Games 一类**（牌桌上实时搜索 + 价值网络）：棋力最强，但每步要大量计算和 GPU 推理，远超 10 毫秒预算。
- **更大的 Transformer**：宽 128、4 层在 JS 里每步就要 28 毫秒；要更大，得把机器人放到有 GPU 的服务器上推理，这是另一个架构。
- **完整 7 人桌翻牌前求解**：Pluribus 级别的算力（数千 CPU 核时），收益有限；翻牌前标准起手牌表已经足够接近均衡。

## 4. 风险

| 风险 | 表现 | 对策 |
|---|---|---|
| 手牌分组太粗 | 同组的牌打法相同，被针对（比如转牌中等牌弃太多） | 阶段 B 细分；阶段 C 用精确解给蓝图打分找出问题格子 |
| 信息集不记完整历史 | 不同行动线共用一个策略 | 键里加行动线特征；阶段 E2 河牌重解 |
| 下注尺寸外的注 | 专门下两档之间的尺寸占便宜 | 阶段 E1 伪调和映射 |
| 评估被运气骗 | 偶然的好结果被当成进步 | 阶段 A 复式对打 + 置信区间，门槛不过就不上线 |
| 三人局不收敛 | 策略来回摆动 | 用平均策略，配合 LBR 和对打检查；不行就只上单挑 |
| 性格层破坏平衡 | Joe、sc 等风格调整引入漏洞 | 性格调整只在合理价格范围内；对打评估时包含性格层 |

---

## 5. 上线流程（每一阶段都一样）

1. 训练完用 `show.py` / `batch.py show` 抽查常见局面合不合理；
2. 打包成试用文件（`--to`），用 `GTO_TABLE=` / `FLOP_TABLE=` 跑阶段 A 的全部评估；
3. 过门槛才写入 `js/` 下的表文件，然后 `npm run stamp && npm run check`；
4. 推到 `main` 自动部署；在 GitHub Actions 确认部署成功；
5. 记录这次的评估数字，作为下次对比的基线。
